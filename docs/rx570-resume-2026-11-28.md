# RX 570 follow-up, 2026-11-28

## Physical page alias correctness

`map_alias` previously removed destination mappings before looking up source
pages. Mapping a range onto itself therefore destroyed its source; overlapping
ranges could lose or replace source pages before they were read. The function
now snapshots and validates every source slice before unmapping. The snapshots
retain section ownership throughout the operation. Unknown source pages fail
before changing the destination. Null-source unmapping remains supported.

The implementation retains the existing page granularity. It does not combine
separate Windows placeholders into a larger mapping.

All 15 XMem tests passed against real Windows mappings. New regressions cover
self-aliasing, overlapping `[A,B,C]` to `[A,A,B]` with a later physical-page
write, and missing source pages preserving the old destination. These tests do
not prove that the alias defect caused the game's watchdog failure.

## Pipeline cache measurements

`VICTORY_PIPELINE_CACHE_TRACE=1` reports successful library loads, misses,
load durations and completed fallback compilations. It does not change shader
translation or the cache keys. Leave it unset for ordinary use.

A copy of the existing driver library and the first 256 selected Series S
recipes were examined without executing the title. The first 16 recipes yielded
23 successful host pipeline loads and zero misses, with a maximum load time of
23.989 ms. A recipe may require more than one host PSO for mesh emulation.

The next run processed the remaining 240 recipes: 312 successful host loads,
zero misses, maximum load time 15,227.449 ms, median 1.024 ms. The final recipe
summary was 255 ready and one previously unsupported shader. The following run
removed only the isolated sample's preparation journal and processed all 256
again using the same executable. It yielded 335 successful host loads, zero
misses, maximum 71.622 ms and median 0.432 ms; the recipe summary was again
255 ready, one refused.

Thus the slow first pass was observed inside successful driver library loads.
It was not a cache-key miss. The same executable's immediate repeat was much
faster. A rebuild preceded the first measurement, but this experiment does not
isolate executable identity, Windows cache residency, or the driver's implicit
cache as the cause. No driver cache was cleared.

These observations qualify the earlier small 128-state benchmark: cache
acceptance and a preparation journal do not guarantee inexpensive first object
creation for every complex shader.

## Launch configuration and remaining limits

The previous game run bypassed object preparation and overrode runtime
compilation to eight workers. Its last loading frames still reported 1,929
pending PSOs. The dump showed a deliberate null write from the game's
30-heartbeat watchdog; it did not establish a physical-memory deadlock.

The local launcher now prepares previously used states before title execution,
uses three runtime workers separately from eight offline compilation threads,
and starts a visible game window. The equivalent command is:

```powershell
$env:VICTORY_PIPELINE_WORKERS = "3"
.\target\release\victory.exe run "<game executable>" --execute --precompile --used-only --console series-s
```

This configuration is being tested; it is not yet a verified fix for the
watchdog. The earlier GPU timeout 0x141 and independently reproduced AMD driver
compiler access violation also remain unresolved.
