# RX 570 follow-up, 2026-11-28

## Physical page alias correctness

`map_alias` previously removed destination mappings before looking up source
pages. Mapping a range onto itself therefore destroyed its source; overlapping
ranges could lose or replace source pages before they were read. The function
now snapshots and validates every source slice before unmapping. The snapshots
retain section ownership throughout the operation. Unknown source pages fail
before changing the destination. Null-source unmapping remains supported.

The implementation retains the existing page granularity. It does not combine
separate Windows placeholders into a larger mapping.

All 15 XMem tests passed against real Windows mappings. New regressions cover
self-aliasing, overlapping `[A,B,C]` to `[A,A,B]` with a later physical-page
write, and missing source pages preserving the old destination. These tests do
not prove that the alias defect caused the game's watchdog failure.

## Pipeline cache measurements

`VICTORY_PIPELINE_CACHE_TRACE=1` reports successful library loads, misses,
load durations and completed fallback compilations. It does not change shader
translation or the cache keys. Leave it unset for ordinary use.

A copy of the existing driver library and the first 256 selected Series S
recipes were examined without executing the title. The first 16 recipes yielded
23 successful host pipeline loads and zero misses, with a maximum load time of
23.989 ms. A recipe may require more than one host PSO for mesh emulation.

The next run processed the remaining 240 recipes: 312 successful host loads,
zero misses, maximum load time 15,227.449 ms, median 1.024 ms. The final recipe
summary was 255 ready and one previously unsupported shader. The following run
removed only the isolated sample's preparation journal and processed all 256
again using the same executable. It yielded 335 successful host loads, zero
misses, maximum 71.622 ms and median 0.432 ms; the recipe summary was again
255 ready, one refused.

Thus the slow first pass was observed inside successful driver library loads.
It was not a cache-key miss. The same executable's immediate repeat was much
faster. A rebuild preceded the first measurement, but this experiment does not
isolate executable identity, Windows cache residency, or the driver's implicit
cache as the cause. No driver cache was cleared.

These observations qualify the earlier small 128-state benchmark: cache
acceptance and a preparation journal do not guarantee inexpensive first object
creation for every complex shader.

## Launch configuration and remaining limits

The previous game run bypassed object preparation and overrode runtime
compilation to eight workers. Its last loading frames still reported 1,929
pending PSOs. The dump showed a deliberate null write from the game's
30-heartbeat watchdog; it did not establish a physical-memory deadlock.

The local launcher now prepares previously used states before title execution,
uses three runtime workers separately from eight offline compilation threads,
and starts a visible game window. The equivalent command is:

```powershell
$env:VICTORY_PIPELINE_WORKERS = "3"
.\target\release\victory.exe run "<game executable>" --execute --precompile --used-only --console series-s
```

This configuration is being tested; it is not yet a verified fix for the
watchdog. The earlier GPU timeout 0x141 and independently reproduced AMD driver
compiler access violation also remain unresolved.

## Game reproduction after preparation

The run started at 01:56 Omsk and restored 2,370 ready previously used
pipeline objects before executing the title; 25 recorded refusals were skipped.
The game created a visible window and rendered thousands of draws per world
frame. Pending PSOs fell to zero to three in several measured frames, but the
image and performance remained incorrect. The user reported black output,
a brief Rockstar Presents screen with audio, then another black freeze.

At one measurement the process had 16,354 MiB private committed memory and a
7,845 MiB working set. The system had approximately 498 MiB physical RAM free.
Host-copy use reached 2,559/2,560 MiB with over 58,000 refused allocations, and
the sampled-texture budget was also full. A later frame lasted 68.5 seconds,
including about 40.4 seconds copying buffers and no pending PSOs.

The new dump again shows the heartbeat watchdog: the deliberate null write at
image RVA `0x23cf683` is inside the callback reached from watchdog RVA
`0x2215c35`. One recording thread waited inside the driver's
`CreateCommittedResource` call while holding the host heap mirror lock; other
recording threads waited for that mirror lock. This establishes an allocation
stall at the snapshot, not a proof of a permanent driver deadlock or the
initial cause of memory pressure. The process exited before the attempted
termination command; it was not successfully killed by the agent.

The following corrections are being prepared and tested independently of
shader translation:

- Release resource references held by completed dynamic descriptor ranges.
  Previously only the slot allocator was updated; stale COM references
  prevented host-copy and texture eviction.
- Associate dynamic ranges with a host heap generation. A list from a destroyed
  heap must not release ranges in a new heap at the same guest pointer.
  Adapted from [VIctory-NVIDIA 47747d6](https://github.com/trustno1-coder/VIctory-NVIDIA/commit/47747d62369a90bd708840622f13c7f55559a6f3).
- Reclaim unreferenced copies of registered buffers without destroying their
  guest resource registrations; keep active lists, descriptors, pending shader
  writes and in-place allocations protected.
- Interleave texture retries with first looks, rotating the first class across
  frames so a short pass cannot permanently starve fresh textures. Adapted
  from [DexNom 5f4c3df](https://github.com/DexNom/VIctory/commit/5f4c3df44197eb03b82205d2da871ded8d0ccf16).
- Query interior committed memory when a streaming texture's first and last
  pages are missing. Adapted from [DexNom 921d8d3](https://github.com/DexNom/VIctory/commit/921d8d3b43b44f3a6ca4b44095edd3c4baf10a87).
- Apply BC7 channel rotation only to modes 4 and 5. Adapted from
  [VIctory-NVIDIA 6726920](https://github.com/trustno1-coder/VIctory-NVIDIA/commit/6726920a8072fe720f908913248cf7407cae25b4),
  originally by fxceless in `06702fe8`.

Initial regression results: 16 descriptor tests, 3 texture-memory tests,
21 shadow tests, and 11 BCPack tests passed. BCPack's two pre-existing ignored
tests are a benchmark and a reference-data fixture. New regressions exercise
real D3D12 reference counts, real Windows mappings, WARP resources, starvation
under a retry backlog, and decoded BC7 blocks. These results do not establish
that the in-game black output, paging or watchdog is fixed.

The completed adaptations and final validation are listed in the
[fork adaptation report](rx570-fork-ports-2026-11-28.md).
