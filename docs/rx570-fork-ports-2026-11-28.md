# RX 570 fork adaptations, 2026-11-28

These changes target the CPU stalls, unavailable streamed resources and retained
host copies seen in the last Series S run. They preserve shader translation
and its existing cache. They have not yet been validated in another game run.

## Additional local ownership corrections

Completed dynamic ranges now release the resources in their `kept` slots before
the allocator exposes those slots as free. Unrelated title slots and ranges
still owned by other lists remain pinned. Submitting a list whose actual
dynamic ranges have already been released requires a new recording; stale
submissions are rejected before entering the queue. This prevents using freed
resource references through recycled descriptors.

Registered buffers can release a cold host copy while retaining their guest
registration. Pressure reclamation and idle sweeps protect copies with command
list references, descriptor references, pending shader writes or in-place
allocations. Lookups update usage and recreate a discarded copy on demand.
The admission path preserves lock order and uses nonblocking cross-cache locks.

## Controls

- `VICTORY_TEXTURE_STAGE_PER_FRAME=0` restores a per-pass time allowance.
- `VICTORY_TEXTURE_STAGE_US` takes precedence over `VICTORY_TEXTURE_STAGE_MS`.
- `VICTORY_TEXTURE_STAGE_BYTES` takes precedence over `VICTORY_TEXTURE_STAGE_MB`.
- `VICTORY_PIPELINE_WAIT_MS` changes ordinary and default screen waits;
  `VICTORY_PIPELINE_WAIT_SCREEN_MS` changes screen waits separately.
- `VICTORY_PIPELINE_WAIT_ONCE_MS` changes the known bake allowance. The bake
  allowance is never below the ordinary allowance.

## Verification and limits

Tests cover shared budgets across concurrent recorders, charging early returns,
long single operations, stale frame accounting, bake classification, actual
D3D12 reference-count release, wrong heap generations, real Windows page
mappings, WARP copy eviction and preservation of active pins, null fence waits,
CPU rewinds, queue writes, direct Windows address wakeups, and decoded BC7 bits.

The combined run passed 192 GPU tests (one pre-existing ignored test) and
104 HLE tests. The final queue suite then passed all 6 tests, including the
last direct address-wakeup regression. BCPack passed 11 tests with two existing
ignored benchmark/reference-data cases. Strict workspace Clippy across all
targets and features passed. The release executable with Agility was rebuilt
after the final source changes.

Lower time budgets can spread texture streaming and new PSOs across more
frames. They cannot make unsupported shaders render correctly. The previous
GPU timeout and independent AMD compiler fault remain unresolved. No RX 570
FPS improvement or removal of the black screen is claimed from unit tests.

The fault-handler plain-copy path, soft views, descriptor synchronization
rewrite, texture heap allocator, and small readonly card buffers were not
ported. They require separate lifetime and fault-path validation.

## Follow-up: memory lifetime, CPU comparisons and shader semantics

A shader-only Series X run after these ports still failed. It used a
3840x2160 display plane and reached about 19-20 GB private memory on the
16 GB test PC. Early world attempts ran very few host draws while more
than 2,000 PSOs remained pending. A later frame spent about 43 seconds;
this is not a 5 FPS or rendering success. The title's own dump writer
then suspended other threads and waited inside a heap allocation. An
external minimal dump was saved before ending that hung process.

The following additions are under local validation, not yet a gameplay claim:

- Move the bindless buffer-range cache from a static map keyed by heap
  address into its owning `HostHeap`. Destroying a heap now releases its
  cached `Arc<Shadow>` references, and a new heap at the same address starts
  with an empty cache. Active recorded lists retain their own copies.
  Two lifetime regressions exercise heap destruction, address reuse and list reset.
- Compare and merge exact bytes with AVX2 when the CPU supports it;
  retain scalar fallbacks for `first_difference`, `last_difference`,
  `changed_runs` and `merge_piece`. Twenty-five shadow tests include random
  unequal lengths, unaligned addresses, vector boundaries, untouched GPU
  inputs and accurate write-result flags. The upstream dword expansion was
  not copied because it could overwrite adjacent bytes written by the CPU.
- Adapt static sampler Phi handling from
  [DexNom ddb7332](https://github.com/DexNom/VIctory/commit/ddb73326b09e600bd2405ee5c987fa611098aaa1)
  and wave64 scalar-mask identity from
  [DexNom 76749ce](https://github.com/DexNom/VIctory/commit/76749ce58da23a43a3500454a8b69c53f05aa477).
  Seven ReflectionMap pixel shaders and one VoxelizeVisiblity shader,
  previously refused, now translate, pass Microsoft DXIL validation and
  create graphics PSOs on the RX 570. Four actual compute readbacks select
  the expected wrap/clamp texels: 9, 3, 9, 3. These changes require a new
  translator-keyed shader preparation pass.
- Offer `run --precompile-bakes` to load and retain only previously
  requested recipes of the four known one-time pixel bake shaders.
  In the failed run, one bake's pipeline became ready about 115 seconds
  after its first bind; the 500 ms wait could not cover that delay.
  Selection reads at most 269 header bytes per requested recipe, skips
  unrelated shader containers and reports refusals before title execution.
  Eight recipe and retention regressions pass. Other PSOs remain on demand.
- Allow bounded presented-frame capture in release builds, without the
  diagnostics feature changing the shader cache identity. PNG limits can
  reserve space for world frames; world detection also observes attempted
  draws so a missing-pipeline black frame can still be inspected.

The broad shader test run without Agility exposed a test environment limit:
24 GPU cases could not find SM 6.6 on the system runtime (hardware 6.5,
WARP 6.2). Running the suite with SM 6.5 exercised those GPU cases, but six
CPU signature tests explicitly expecting SM 6.6 barycentrics rejected that
profile. These two broad commands are not reported as passing suites.
The changed lowering cases pass separately; the new shader regressions above
were explicitly executed on hardware with the app-local Agility runtime.

A separate wave32 audit also corrected a count: 107 native compute variants
with groups larger than 32 were found in a container census; they are not
107 demonstrated PSO refusals. Six plain candidates already validate and
create hardware PSOs with no wave operations and no WaveSize metadata.
No blanket WaveSize replacement was made.

## First world-frame failure with the Series S memory profile

The 04:30 Series S run reached the loading illustration after confirming
the local Player selection. Before its first world frame completed, the
title's watchdog deliberately wrote to address zero. This dump is not an
AMD shader-compiler access violation. The process reached 11–12 GiB private
memory, with approximately 600 MiB free physical RAM at the lowest sample.
The GPU process counters showed about 2.62 GiB dedicated and 3.48 GiB shared
memory. Shared memory is expected here: host buffer copies explicitly use
WRITE_BACK/L0 heaps, including the CPU staging half of card-backed copies.
Raising the card-buffer cap alone does not remove that staging memory.

The initial indexed-buffer pass visited 71,757 slots, found 4,948 copies
covering 1,631 MiB, and took 13,173 ms. Later host-copy requests hit the
2,560 MiB profile cap; at least 1,025 requests were refused. The recorded
loading-screen 30 FPS is not world performance.

The dump also caught a recording thread calculating a texture footprint.
That query built full mip and block-address tables before checking the
budget, even for an already-created texture. Allocation-only queries now
share the layout calculation without constructing those tables; existing
host textures return before budget evaluation. These are small repeated
allocations, not a demonstrated multi-gigabyte temporary allocation:
block-axis offsets occupy at most 2,052 bytes per plane in the tested
modes. Tests compare size/alignment across 48,960 descriptions, and retain
the full layout's addressing and detile round trips. This optimization
alone does not establish the cause of the watchdog or a frame-rate gain.

Further investigation found that a failed buffer-copy allocation could
leave a descriptor null while its generation was marked complete. A later
successful copy lookup did not remake the descriptor. Descriptor creation
now distinguishes a temporary budget refusal from an invalid view. Only
the former retries, at most once per presented frame, after rechecking
the view generation. Six tests exercise real CBV/SRV/UAV allocation pressure,
recovery without rewriting the descriptor, invalid caching, stale generations
and oversized allocations. Production memory caps are unchanged.

Initial indexed-buffer preparation now retains a cursor and changed-slot
queue, sharing 16 ms and 32 MiB across heaps per presented frame. The
coordinator rotates the first job between active heaps and counts unique
copy IDs by actual D3D12 buffer width. It keeps weak references for accounting;
these do not pin the copies. Repeated audits preserve ready ranges and
progress through a pending scan. Existing buffers still refresh, and direct
or table accesses bypass this preparation budget. A new disjoint range of
an already-known copy refreshes even if that copy was seen earlier in the
same frame. Invalid null descriptors cannot enter the ready cache.

Eight new tests and two existing multiple-heap regressions pass, including
concurrent permits, eventual progress, alias accounting, real refresh while
another heap is pending, and retry after freeing a real budget filler.
Progress logs distinguish preparation time, ready refresh time and pending
views. One indivisible allocation may exceed a budget; ready refresh and
bookkeeping are outside it. No gameplay success or fix for the earlier
desktop-wide GPU timeout is claimed from these tests.

## Live partial interpolation and packed integer kernels

The pixel shader `38bf0814e721a1b3` lost a live first-half interpolation
result. Its reported failure at the export was deferred from a packed
half-register write that preserved that intermediate value. `io::raise`
now retains first-half results read outside a folded interpolation pair,
including through Phi values, as the exact `P0 + i * (P1 - P0)` expression.
Ordinary complete pairs remain folded. This follows the live-P1 handling in
[avatarmanz 014d52d](https://github.com/avatarmanz/VIctory-7900XTX/tree/014d52dedf837d1ac660a0bd256c4704be9eeb40).
Nine I/O tests pass. RX 570 SM 6.6 readbacks match 512 scalar comparisons;
the real `38bf0814e721a1b3` and `007bb29b393d08c5` shaders validate and
create graphics PSOs.

Two failing compute kernels came from `amd_fidelityfx_upscaler_xbox.dll`.
They exposed SCC used as integer data, SCC derived from a lane mask, and
packed signed-byte dot products. The SCC changes use the existing condition
value and wave-identity handling. They do not substitute wave64 for wave32
or turn unknown masks into zero. The dot products use signed byte
multiplication and wrapping 32-bit addition, retaining the full accumulator.
VOP3P source-half selectors are applied independently to both multiplicands.
The implementation adapts the
[pinned fork's dot semantics](https://github.com/avatarmanz/VIctory-7900XTX/blob/014d52dedf837d1ac660a0bd256c4704be9eeb40/crates/victory-shader/src/emit/lower.rs#L8771-L8825)
and the [AMD RDNA 2 ISA](https://docs.amd.com/api/khub/documents/Et~wpu9g~Ffl7d9q0QZ~Og/content),
printed pages 165 and 263. The SCC recovery and portable arithmetic are
local adaptations.

Hardware tests cover scalar SCC zero/one, wave64 zero/low/lane-33 masks,
eight compact dot-product edge cases, and 192 VOP3P selector/accumulator
readbacks. The first attempt still refused `8b437ab61d8008fe` at a whole-wave
section; that failed combined command is retained in the local test evidence.
The later exact post-section lane-read fix makes both real kernels translate,
pass Microsoft DXIL validation and create RX 570 compute PSOs in SM 6.5 and
SM 6.6. The simulator keeps an unknown whole-vector shape when the two halves
contain different reductions. Only a proved scalar read after restoring the
same EXEC is folded. Eleven CPU tests cover valid and invalid lane reads and
EXEC changes; 640 hardware output values cover full and partial active masks.
This adapts the
[pinned fork's whole-wave lane analysis](https://github.com/avatarmanz/VIctory-7900XTX/blob/014d52dedf837d1ac660a0bd256c4704be9eeb40/crates/victory-shader/src/emit/wave.rs#L143-L207)
with a conservative restored-EXEC check.

Packed dot products now emit standard DXIL `Dot4AddPacked` opcode 163 after
the exact source repacking. Microsoft specifies these intrinsics as required
in [Shader Model 6.4 and later](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/hlsl-shader-model-6-4-features-for-direct3d-12);
this does not imply a dedicated integer-dot instruction on Polaris. All 200
numeric cases pass on the RX 570 separately in SM 6.5 and SM 6.6. For the two
real kernels, SM 6.6 DXIL sizes fall from 118,636 to 59,600 bytes and from
792,136 to 344,696 bytes. Warm driver-cache PSO creation measured 4.8/25.6 ms
versus 11.1/84.9 ms for the manual arithmetic; this is not a controlled cold
compile or game performance comparison.

The following Series S game test still produced black world frames and
eventually aborted through an explicit null-write fatal path. Short intervals
reached 2–3 FPS, with long stalls. A new unrelated compute PSO took 117 seconds
to compile while the process peaked at about 16.5 GiB private memory. Its
verified container `50949ebfee9eb51d` has no packed-dot instructions, so the
dot change cannot improve that particular shader. These runtime observations
precede the whole-wave and intrinsic changes; their effect on the black world
still requires another game test.

The full GPU suite after the buffer changes passed 242 tests with one
existing ignored test. Shader source changes require one new cache preparation
pass before the next game run. Rendering-only rebuilds continue to reuse it.

## Ready-buffer refresh and stale object views

The second buffer iteration distinguishes a pacing token from an actual
present. A heap's full cached-ready walk runs once per presented frame.
New views retain their own first upload. Within one command-list recording,
already-covered intervals of an unwatched copy are omitted, while disjoint
intervals still refresh. Coverage includes a unique recording ID that changes
on Reset: a recorded but unsubmitted list cannot suppress a new alias's
upload in another list. The previous per-frame owner assumption for the full
cached-ready walk remains; no new execution dependency between lists is
invented. Direct and table accesses still refresh through their existing paths.
The `VICTORY_UNWATCHED_FRAMES` experiment retains its interval in presented
frames; newly admitted ranges bypass it.

Resource release now publishes an object-view generation epoch. Before
allocating new copies, heaps check their ready object records in a batch and
clear stale slots without creating a resource. The invalidate-only path
rechecks the expected key, current record and made slot. It preserves address
views, newer generations, live aliases and resources pinned by recorded
lists. Reaping does not wait behind the cold-allocation budget. Range cache
and view-registry locks are released before descriptor cleanup and retirement.

New counters distinguish full ready batches, cold jobs, refreshed bytes and
ranges. Cleanup reports stale slots, unique affected copy bytes, elapsed time
and sampled global LIVE before/after. Affected bytes are not bytes freed;
other concurrent allocations and releases can affect the global sample.
Only controlled tests establish causal LIVE changes. The effect on actual
RAM use, image correctness and FPS still requires a new game run.

## Morning preparation and controlled run, 28 November

The final normalized release passed 242 GPU tests (one existing ignored test),
strict workspace Clippy, the text-asset policy and release compilation. The
new shader preparation completed with 25,635 ready and 254 refused records
from shaders.rpf, plus 614 duplicate records. The upscaler DLL prepared 24 of
29 records. Of 2,606 previously requested Series S pipeline recipes, 2,541
were ready, 65 refused and none unreadable or left to process. This is the
used-recipe selection, not all recorded pipeline states.

The controlled 14:25 run reached local Player selection and rendered the
stylized tiger and opening credits. The 500-draw capture heuristic triggers
on these credits too; it does not prove that gameplay has started. After the
animated title cards, multiple manual captures several minutes apart remained
black. Short timing intervals reached 5.1 and 5.4 FPS, but later intervals
fell to approximately 1–2 FPS with long stalls. Normal gameplay graphics and
sustained five FPS were not achieved. The parent stopped this controlled run
at 14:52 to free the GPU for targeted tests; that exit was not a crash.

On an unchanged present the full ready-refresh counters remained unchanged,
confirming that repeated recording calls no longer repeat that complete
refresh. The run still reached the 2,560 MiB host-copy admission cap. Resource
reaping found 62 stale slots by one sample but demonstrated no large RAM
reduction. Peak process private memory reached 18.44 GiB, with 8.57 GiB
working set and about 0.54 GiB free physical memory. Dedicated GPU allocation
reached approximately 7.52 GiB, plus 5.16 GiB shared memory. These counters
are different memory measurements and must not be added as physical RAM.

A 2,604 ms timing interval spent 2,296 ms waiting on GPU/readback, with
2,231 ms attributed to fetching changed card-copy pieces; these overlapping
measurements must not be summed. Pending pipeline count was zero in that
interval. Memory pressure coincides with the stalls, but a residency trace
would be needed to establish the exact paging cause.

The FSR4 postpass fdce2a0a9fb1521a still fails RX 570 pipeline creation in this
run. Its shader requests wave32 for a 256-thread group and uses read-first,
read-lane, lane-index and ballot operations. Removing WaveSize metadata alone
would change those operations' semantics on a physical wave64 device. A
restricted half-wave implementation is under investigation; its runtime
correctness and effect on the final display have not yet been established.
